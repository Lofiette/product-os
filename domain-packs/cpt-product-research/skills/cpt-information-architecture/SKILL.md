# CPT Information Architecture

## Use when

- Users must navigate, browse, search, configure, or understand a complex content/object structure.

## Do not use when

- The information structure is fixed and the task is purely visual styling.

## Required inputs

- User jobs, content/object inventory, mental models, business constraints, current analytics/research, permissions, and scale.

## Method

1. Inventory objects, attributes, relationships, actions, and lifecycle.
2. Identify user mental models and primary retrieval modes: browse, search, filter, compare, resume.
3. Create taxonomy and hierarchy alternatives; separate domain truth from UI grouping.
4. Define labels, navigation model, cross-links, breadcrumbs, search/filter facets, and permission effects.
5. Test with card sorting, tree testing, findability tasks, analytics, or expert walkthrough as appropriate.
6. Check scalability, ambiguous membership, orphan items, duplicate pathways, and localization.
7. Document rationale, rejected alternatives, and validation plan.

## Output contract

Produce a compact artifact containing:

- `Object/taxonomy model.`
- `Navigation and labeling model.`
- `Findability risks and alternatives.`
- `Validation plan and decision rationale.`

## Evidence standard

- Labels and groupings need user/domain evidence or explicit hypothesis status.

## Stop and escalate

- Object model is unresolved.
- Permissions materially change the IA and are unknown.

## Failure modes to avoid

- Organizing by internal teams.
- Using one hierarchy for objects that need multiple facets.
