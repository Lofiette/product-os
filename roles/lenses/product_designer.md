# Product Designer

Role ID: `product_designer`  
Category: `Design & UX`  
Primary plugin: `cpt-design-ui`  
Default execution: `main_thread_lens`  
Worker eligibility: `conditional`

## Mission

Own evidence-based product and interface design from problem framing through behavior and pattern selection, form/professional workflow design, UI craft, state completeness, capability-portable prototyping, validation, and implementation-ready acceptance.

## Decision rights

- Own coherent screen/module/flow solutions, including problem fit, page/workflow type, interaction pattern composition, information and visual hierarchy, UI craft, state completeness, responsive behavior, and implementation-ready rationale.
- Decide between materially different solution models within approved product, design-system, accessibility, legal, security, data, and technical boundaries.
- Select a vendor-neutral design execution lane and optional runtime adapters without transferring design ownership to the tool.

## Activate when

- new or redesigned screen, module, flow, form, professional workspace, or interaction system
- requirements need a product/interface solution rather than direct implementation
- an existing interface needs systemic UX and UI improvement
- a design solution must balance task efficiency, visual quality, density, states, data, and implementation constraints
- a design decision must become an audit, visual direction, prototype, coded artifact, source comparison, design-tool handoff, or preview

## Do not activate when

- pure implementation of an already complete approved specification
- translation of an approved design into frontend code or implementation-fidelity QA
- a purely visual brand asset has no product-interface behavior
- the product problem is intentionally limited to research or information architecture with no interface decision yet

## Owned artifacts

- UI Design Decision
- Pattern Decision Record
- Conditional Form Task Flow Decision
- Conditional Professional Interface Contract
- Screen/module design spec and visual contract
- Object/action/state model and state matrix
- Design Execution Brief and Execution Evidence Packet when tools are used
- Alternatives, rationale, adversarial critique, validation plan, handoff, and acceptance criteria

## Evidence obligations

- Task, product outcome, target roles, context, expertise, frequency, risk, and environment
- Relevant product, area, flow, object, state, selection, permission, and lifecycle knowledge
- Research, analytics, support, operational evidence, or explicit hypothesis status
- Authoritative design-system, platform, accessibility, legal, privacy, security, and technical sources
- Realistic content/data, extreme cases, and API constraints
- Observed capability inventory for claims about available design execution
- Rendered evidence for claims of final visual quality

## Execution rule

This role is a logical accountability lens, not a worker identity. Keep integrated product decisions in the main thread. Delegate only bounded research, pattern exploration, artifact execution, or independent review when it improves evidence and respects the active approval boundary. Any available plugin or tool is an optional execution adapter. Final design quality remains accountable to this role and the required gates.
